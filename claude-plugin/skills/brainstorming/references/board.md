# Brainstorm board — full flow and payload contracts

SKILL.md "Visual surface" owns the board-vs-terminal judgment and the just-in-time offer; this file owns the mechanics.

**Reliable writes:** pass a stable `requestKey` on `compose_board` and `update_cards` for one logical operation. Retry identical accepted input with that same key after a lost response; the server returns the original receipt without duplicating. Changed input needs a new key; reusing the old key returns 409. REST also accepts `Idempotency-Key` (both names must agree). Read the returned card IDs and refs for follow-up edits; let the server size and position the composition. A saved-template retry replays the first committed expansion even if the template has since changed.

**Brainstorm boards are DOCUMENTS:** compose in narrative order and NEVER pass x/y. The `decision-map` template puts the board in `flow: "document"` — top-level blocks stack top-to-bottom in compose order, and the mode STICKS: every later free batch starts a new row below. Reading order: ground-truth imports → the map heading → one chapter per decision (its per-option diagrams and takes INSIDE it) → working-notes section → log page. A batch composed out of order lands out of order — there is no re-shuffle step. (Non-brainstorm boards keep the default aspect-packed shelf rows; opt any board in with the top-level `flow: "document"` param.)

**Say how the batch FLOWS:**

- "these three on one row" = an UNTITLED cluster `{kind:"cluster", payload:{layout:{mode:"row"}}, children:[…]}` — untitled clusters render NO chrome. `{mode:"grid", cols:N}` for N-across.
- Sections take `payload.description` — one quiet line under the kicker title; frames render as HEADED GROUPS (border only on hover/selection), so members' own card faces are the only boxes.
- The top-level `aspect` param (0/omit = 1.6, clamped [1, 3.2]) sets the shelf target per batch: wider (2.2–3) spreads a shallow narrative, squarer (1–1.3) suits deep stacks.

**Before any mockup, load the design system.** Resolve and read the surface's `DESIGN.md` (per-surface in monorepos — `apps/client/DESIGN.md` vs `apps/web/DESIGN.md`; ask if ambiguous) and build every variant from its actual tokens. None → offer to create one first (the `learn-design` skill).

**Mechanics** (vitrinka MCP tools first, raw API as fallback; artifact bundles are self-contained single-file HTML — no external hosts, same contract as the `artifact` skill):

1. **Create the board** (idempotent, 409 = reuse):
   `POST {base}/api/v1/boards` body `{"slug":"<project>-brainstorm-<topic>","title":"…","board_type":"brainstorm","project":"<project>","subgroup":"brainstorming"}` — `project` files it under that project's group; `subgroup` folds it under the project's *brainstorming* sub-group (inferred from the board_type when omitted; projectless boards fall back to the *Brainstorming* type group). A board whose deliverable is design directions/mockups rather than a decision map takes `"subgroup":"design"` — `design` is never inferred, always pass it.
2. **Compose the decision map with the BUILT-IN `decision-map` template — one `compose_board` call**: `{"template": "decision-map", "params": {"title": "…", "context": "2-3 lines — what exists, what's missing", "decisions": [{"key": "D1", "title": "…", "stakes": "…", "options": [{"label": "…", "hint": "why / tradeoff", "recommended": true}], "multiSelect": false}, …]}}`. The server lays it out as DECISION CHAPTERS: a wide context strip, then ONE `section` PER DECISION titled exactly `"<key> · <title>"` (`D1 · Board grammar`), described by its stakes, the entry first and the decision's evidence beside it. There is no outer map section. **The chapter title IS the landing contract**: `compose_board {section: "D1 · Board grammar"}` and `POST …/artifact {section: "D1 · Board grammar"}` drop cards into that chapter, which grows to fit. Never hand-compose a heading + idea-card + question column. Option `hint`s render VISIBLY under each label and `recommended` shows as ★ — put your recommendation's why in the hint, always. **Options keep their NATURAL order** (A, B, C…; chronological; small→large): never reorder to put the recommended option first — the terminal recommendation-first rule is terminal-only. A decision the user should answer in prose takes `"kind": "text"` instead of options. Max 12 decisions — a bigger map means the brainstorm needs splitting.
   **Existing system? Import the ground truth**: an importable truth source — `docker-compose.yml` (`compose`), an OpenAPI spec (`openapi`), SQL DDL (`sqlddl`), a live Postgres (`pgschema`) — becomes a refreshable "what exists today" diagram beside the context strip: `REV=$(git rev-parse --short HEAD); vitrinka board diagram import <file> --board <slug> --rev "$REV"` (raw: `POST {base}/api/v1/boards/{slug}/import {kind, source, ref, rev, title}`). Skip when the topic is greenfield.
3. **Brainstorm around the fork with the cheap vocabulary before mockups**: `cluster` frames per direction (`children: [refs]`) holding `idea`/`pro`/`con`/`risk` text cards; a `chart` card for structure — `matrix` (effort × impact), `flow`, `bars`/`timeline`, real charts (`line/area/scatter/pie/donut/heatmap`, recharts-shaped `{series|items}` data) when the fork is data-shaped; a `table` card (typed columns — options × criteria) for a comparison grid; a `diagram` card when the fork is ARCHITECTURE-shaped (lanes/groups/nodes/styled edges, server-laid-out). **For an architecture fork, typed diagrams per option are THE standard, not optional prose**: one small diagram card per competing architecture (typed nodes `service`/`entity`/`endpoint`, edge styles `default|public|mesh|internal|outbound` — `accent` is a node/group TONE, never an edge style; vocabulary in the artifact skill's `references/diagram.md` and the cheat sheet below), and the decision's options trace to them via **`cardRef` in the SAME compose call** — pass the diagram cards (each with a `ref`) alongside `template`/`params`, each option carrying `{"cardRef":"<that ref>"}` (`cardId` still works for pre-existing cards). **Every card an option `cardRef`s lands INSIDE that decision's chapter automatically** (entry first, diagrams beside it in option order; a ref cited twice joins once, a ref cited by two decisions joins the first) — never wrap them in a section of your own or land them with `{section}`. A `cardId` option is left where it is. Competing architectures must be visually comparable at a glance. A chart is ~100-300 tokens; an artifact is a whole HTML document — spend that only on step 4. For journey-shaped work, `section` frames (journey-named, always visible, pill-navigable) partition the board; scope later reads/writes with `scrape_board {section}`, `compose_board {section}` and `arrange {scope:"section:Name", gap, cols}`.
4. **Visual takes live INSIDE the decision's chapter** — two calls total:
   1. Per take, `POST {base}/api/v1/boards/{slug}/artifact` with `{"body":"…","runtime":"tw4","tokens":{…},"title":"A — <name>","section":"<key> · <title>","device":"phone"|"tablet"|"web"}` (or `"html"` for a full document, ≤8 MiB) — `section` is the decision's CHAPTER TITLE exactly as composed (`D3 · Panel anatomy`), never a "Take A — …" section of your own. The server measures the natural size — mocks always render whole, scaled to the card. A tradeoffs text card per take goes the same way: `compose_board {section: "<key> · <title>", cards: [...]}`. **Never send x/y or w/h; `device` is MANDATORY intent** (default is 16:10 web — phone mockups without `device:"phone"` render wrong). **Paint your own page**: the artifact iframe face is WHITE and blob URLs are immutable-cached. A dark `body`/`runtime:"tw4"` mockup must START with `<style>html,body{margin:0;background:<bg>}</style>` (a `min-h-screen` div does NOT reach the iframe edges) — a full `"html"` document styles its own `html`/`body` in its `<head>` (it must stay a real document; a fragment starting with `<style>` is rejected). tw4 markup uses raw `class=`, never JSX `className=`. Outside the chapter pattern, `"anchor": <cardId>` + `"side":"right"|"below"` docks a one-off mockup beside any card; coordinate-free posts land in free space, never at (0,0).
   2. Link the takes to the decision: `update {kind:"question", id, options: [{"label":"A — <name>","hint":"<why>","recommended":…,"cardId":<that take's artifact id>}, …]}` on the chapter's question (id in `get {kind:"questions"}`); a decision that only exists because of the takes composes as `{template:"decision-map", params:{title:<the map title>, extend:true, decisions:[…]}}` with `cardId` on each option instead. The board draws a trace wire from the question to each option's mockup and picking zooms to that take — never ship an option without its `cardId`.
5. **Refine in place, don't re-compose**: `update_cards` rewords your own cards (AI layer only) and removes what you own — AI-layer cards, section frames, cards you created — up to 25 per call / 30 % of the board. Removing the user's content answers `409 needs_confirm` with a `preview`; read it, repeat the same ids with `confirm:<token>` + a `reason` (≥ 20 chars). Removals are soft; the reason shows in HISTORY and the Trash tab, where the operator restores. Everything you place sits under the board's `✦ eve` toggle.
6. **Hand over the URL**: the `url` field the create-board response returned — server-authoritative, carries the `/w/<workspace>` segment; never compose `{base}/boards/{slug}` yourself. Continue any terminal questions in parallel.
7. **Collect answers**: answers are STAGED — the user picks, then presses "Send to Claude" (↑) to release them, so they arrive as a BATCH of `choice` items on the work wire (multi-select answers carry `options: [labels]`). A choice item may carry a **`note`** — the operator's clarifying words attached to the pick: part of the answer, never ignored. Answer/note text may contain **⌖E tokens**; the item's **`refs`** array resolves each — `{token, cardId, elemNo, region?, node?, crop}`, `crop` a ready image URL of exactly the pointed-at region — fetch the crop when the pointed pixels matter. A `kind: "text"` item's `option` IS the typed prose answer. **Listen on the highest rung this harness offers** — the `docs {topic: "guide:listening"}` ladder, announced once; on rung 3 loop `wait_for_work {board, timeoutSec: 50}` and never end the turn on your own — a turn that ends here ends the brainstorm. Whichever rung: drain the batch from `choices[]`, **read the answers carefully — they may request clarification, changes, or that you not proceed — and follow what they actually say**, write the log, compose the next frontier, go back to listening the same way. `get {kind:"questions", board}` reads the full question record without holding the wire (staged answers are visible but NOT yet sent — don't act on them). Choices ride the wire exactly ONCE — a send while no session was listening is NOT lost: `get {kind:"questions"}` is the durable record (answer, note, refs, answeredBy, staged/sent per question) — reconstruct the batch from it. Record each answer, notes included, in the decision log. **The log page is LIVE**: after draining each batch, update the spec (answered rows flip to `[!status green](Decided)` with the call), commit, and `POST /cards/{id}/refresh` the log page.
7b. **↻ REGENERATE — the operator's rework signal**. ↑ Send releases a plain batch; **↻ Regenerate** releases it with `regenerate: true` on every choice item. Never retract, rewrite or re-compose open questions off picks that have not been released, and never treat a drained plain batch as a rework request:
   1. **Plain ↑ batch**: record the answers, compose NEW dependent-round questions if settled answers opened them (`extend: true` — new chapters append below the last one). Existing open questions stay untouched.
   2. **↻ regenerate batch**: the operator says the remaining open questions no longer fit — discard them and compose a fresh frontier following the direction these answers set (reread notes and Other write-ins first). The client confirmed the discard; regenerate without re-asking. First `board_working {board, status: "recomposing — rethinking N questions…", expected: N}` (`board_working` and `retract_questions` are `rare`-module tools — opt in on the registration's `/mcp` URL with `?modules=core,rare`), then retract + replace, one living map: `retract_questions {ids}` withdraws your stale OPEN questions (never the operator's answered/staged ones — those 409 per item) and `update_cards {remove: [ids]}` removes their chapter sections in the same breath — list the section id AND the entry / evidence card ids inside it (trashing a frame never trashes its members; `scrape_board {section: "<key> · <title>"}` lists them); `update {kind:"question"}` rewords a fork that survived in changed shape. Then compose the next frontier: `{template: "decision-map", params: {title: <the SAME map title>, extend: true, decisions: […]}}` — extend skips the heading and appends one chapter per decision below the existing ones. Do NOT pass `section`. Retracted rows stay visible in `get {kind:"questions"}` (`retracted: true`) — never re-ask them verbatim.
   3. **Pivot flags**: mark map-reshaping decisions/options `"pivot": true` — render emphasis only; the flag streams or flushes nothing.
   4. **Log per batch**: refresh the log page after each drained batch.
7c. **✦ ASK-AI info requests** — `asks[]` items (`{type:"ask"}`) on the same wire, arriving IMMEDIATELY (never staged): the operator wants more information about ONE question before picking. Service asks FIRST, before any batch work. STREAM via `answer_ask {id, text, partial:true}` in 2-4 sentence-sized chunks, final chunk without `partial` (settles ✓ done; `failed:true` + a reason settles ✗ failed). Ground the answer in the real system — read the code if the ask is about behavior — and keep it popover-sized: the item carries the question's prompt, stakes and option labels, so answer about THOSE. An ask never changes the map: no retracts, no recompose, no code edits.
8. **Settle: finalize the log, graduate** — when all map questions are answered:
   1. **Log page card, mdfile-backed, born WITH the board**: the initial build composes the log page (all rows Open) as `{"kind":"page","payload":{"md":"<log md>","source":{"kind":"mdfile","ref":"<spec path>.md","rev":"<git short SHA>"}}}` — the spec file and the board page are ONE artifact. At settle, commit the final spec and push the last `POST {base}/api/v1/cards/{id}/refresh {source:<md>, rev:<new SHA>}`; if a human block-edited the page meanwhile, run the write-back loop from the artifact skill's `references/pages.md` first.
   2. **The log is a live index**: the spec's decision table as `:::table` with a status column of `[!status green](Decided)` lozenges (`[!status yellow](Open)` for deferred), a `[!date](YYYY-MM-DD)` chip in the header line, and per-row `#E<elemNo>` links to each decision's tile (elemNos from the compose response or `scrape_board`). The rich syntax lives in the committed file too; it degrades to literal text outside the board.
   3. **Graduate to the docs board, automatically** (no ask): `list {kind:"board", project}` finds the project's docs board, create it if missing (`create {kind:"board", slug:"<project>-docs", board_type:"docs", project, subgroup:"docs"}` — 409 = reuse), push the log page (same mdfile-backed contract, into the **Pages** section) and re-compose the WINNING architecture diagram (into **Architecture**) — re-compose, don't move: the brainstorm board keeps its full option history. `#E<elemNo>` links are BOARD-LOCAL — strip them (or retarget to the graduated diagram's elemNo) in the docs copy. Hand back both board URLs.

**Payload cheat sheet** — the CANONICAL element vocabulary (the retired `viz` kind and its payload shapes 400). Full per-kind contracts: `docs {topic:"<kind>"}` — generated from the validator; kind index: the publish skill's `references/card-kinds.md`:

```
text     {"kind":"text","payload":{"md":"…","role":"idea|pro|con|risk"}}
         idea/pro/con/risk are ROLES on text cards — never card kinds
heading  {"kind":"text","payload":{"md":"# …","role":"heading","level":1|2|3}} — the editorial ladder (30/22/17px):
         level 1 = the board's H1 (decision-map mints its own), 2 = chapter intro, 3 = sub-heading; deeper #s step down a tier
chart    {"kind":"chart","payload":{"viz":"<viz>","title":"…"?,"caption":"…"?,"data":{…}}}   viz + data are REQUIRED; fill the ONE slot the viz reads:
         viz line|area|bars|scatter → data.series [{"label":"web","points":[120,180,240]}] (+ "x":["W1","W2","W3"] categories;
           scatter points are [x,y] pairs ONLY; bars also accepts data.items labeled rows) · "stack":true groups→stacks
         viz pie|donut|bars → data.items [{"label":"…","value":<number>}]        viz stat → items [{"label","value","delta"?,"unit"?,"tone":"good|warn|bad|neutral"?}]
         viz timeline → items [{"label","when":"2026-09-05"}] · viz matrix → items [{"label","x":0..1,"y":0..1}] · viz flow → items [{"label"}]
         viz heatmap → data {"x":[<col labels>],"y":[<row labels>],"values":[[n,…],…]} — one row of numbers per y label
         (a "table" is a KIND, never a viz — the retired viz:"table" 400s)
table    {"kind":"table","payload":{"title":"…"?,"caption":"…"?,"cols":[{"key":"opt","label":"Option","type":"text|number|date|select|check|link"}],
                                    "rows":[{"opt":"Hub","score":3}]}}
         rows are objects KEYED BY COL KEY (no "id" field, never positional arrays); every row key must be a declared col key
         (unknown key = 400); type defaults to text; select cols carry "options":[…]
diagram  {"kind":"diagram","payload":{"title":"…","dir":"LR"?,"nodes":[{"id":"api","title":"API","type":"box|service|entity|endpoint|note"}],
                                      "edges":[{"from":"api","to":"db","style":"default|public|mesh|internal|outbound","label":"…"?}]}}
         nodes carry title, NEVER label (id auto-assigns n1, n2… when omitted; edges reference ids, or node.port)
         edge style has NO accent — accent is a node/group "tone" (default|public|mesh|internal|outbound|accent)
         lanes [{"label":"…","nodes":[…]}] (label, not title) · groups [{"title":"…","tone":"…"?,"nodes":[…]}] (title, no id needed)
         entity columns [{"name":"…","type":"…","pk":true,"fk":"table.col"}] — fk is a STRING ref, not a bool
         endpoint titled "POST /path" derives its method chip + path; omit w/h (natural size, no upscale)
frames   {"kind":"cluster|section","children":["ref",…],"payload":{"title":"…","description":"…"?,"layout":{"mode":"row|grid|column","cols":N,"gap":N}}}
         children order is reading order, independent of cards array order; payload.layout retains the frame's arrangement
         untitled cluster = chrome-free row/col group (no box, no label); section description = one quiet line under the kicker
aspect   top-level compose param {aspect: 2.4} — shelf target w/h (omit = 1.6, clamp [1, 3.2]); spread wide narratives, don't stack them
flow     top-level compose param {"flow":"document"} — chaptered top-to-bottom reading order, sticky on the board;
         the decision-map template sets it automatically
page     {"kind":"page","payload":{"md":"…","source":{"kind":"mdfile","ref":"<spec path>.md","rev":"<short sha>"}}}
option   {"label":"…","hint":"…","recommended":true, "pivot":true?, "cardRef":"<ref in THIS batch>" | "cardId":<existing id>}
         options stay in NATURAL order (A/B/C…) — ★ marks the recommendation; never sort recommended-first on a board
pivot    decisions take "pivot":true (question-level) or per-option — marks the map-reshaping fork (render emphasis only; nothing streams)
extend   decision-map params {"extend":true} appends one chapter per decision below the map, no heading (next rounds)
chapter  every decision composes as a section titled "<key> · <title>" (D1 · Board grammar) with description = stakes;
         {section:"<that title>"} on compose_board / POST …/artifact lands takes INSIDE it; option cardRef cards join it automatically
stakes   first-class on questions: decision-map flows each decision's stakes onto its question automatically;
         ask_board / compose questions / `update {kind:"question"}` take "stakes" directly — the answering panel renders it
         under the prompt and the choice work item echoes it, so ALWAYS pass it for decision-shaped questions
verdict  choice items from brainstorm boards may carry {ranking:[best-first], discarded:[]} — read it as the operator's
         whole preference: log runners-up and dead options, not just the pick
```

**The Plan chapter — the board's last section, read alone.** `compose_brief {id: <epic>}` appends (or rebuilds in place) ONE final section titled `Plan` at the bottom of the document flow: the intent (one text card), each decision's CHOSEN take only — the winning option's `cardRef`/`cardId` card portalled or ref'd into the chapter, never copied — the architecture diagram, and the acceptance checklist. Rejected takes stay in their decision chapters. The implementing session reads it with `scrape_board {board: "<slug>", section: "Plan"}`, which is what `pickup` prints under "read on demand" for the brainstorm board ref (`meta.load: "on-demand"`, `meta.section: "Plan"`). Never compose a Plan section by hand and never add takes to it through the `{section: "Plan"}` door — it is server-owned and the next `compose_brief` rebuilds it.

**Fallback ladder** — never block the brainstorm on the board, and always SAY which rung you're on: `compose_board` → (tool missing / 404 = older deploy) `ask_board` + artifact cards → (server unreachable) terminal-only `AskUserQuestion`.
