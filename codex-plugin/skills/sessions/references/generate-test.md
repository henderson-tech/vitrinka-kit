# Stage: generate-test — from recording to journey tests

For fixing the session's issues, use the fix stage (`fix.md`, this directory).

A human walked the app while the recorder captured every screen, click, and
route. That walk is a REAL user journey — more truthful than any synthetic
test plan, and the most valuable thing to pin as a regression test. The
failure modes this skill exists to prevent:

1. **Duplicate journeys** — the 5th test of the same functionality is
   maintenance debt, not coverage. The registry verdict comes BEFORE any code.
2. **Re-implemented page interactions** — N journeys re-writing login/nav
   selectors drift independently. Shared blocks (PageObjects) are the dedup
   layer; journeys compose them.
3. **Traversing the raw session** — ONE `get_session` call is the whole read.
4. **Untracked work** — a generated test the registry doesn't know about will
   be regenerated by the next session. Every run ends with manifests written.

Input: a session board slug or URL (`/vitrinka:sessions acme-session-7
test`) or a numeric session id. Run FROM THE APP'S REPO. Work in a
worktree (repo's own `wk:*` command when mapped, else
`git worktree add .worktrees/testgen-session-<id> -b test/session-<id>`).

## Phase 0 — read the session and the registry

1. `get_session({ board: "<slug>" })` — steps (route walk, actions, hosts),
   issues, facets. This is the journey source; never read `/events`.
2. Read `.vitrinka/journeys.json` and `.vitrinka/sessions.json` (schemas in
   `registry.md`, this directory; both may not exist yet — treat as empty).
   When the feature has a QA plan, read it too: `vitrinka task resolve-qa
   --json` (the branch's `vt-<id>`, or `--task <epic|qa>`) → `get_task
   {id: <qa>, include: [children]}` lists the `journey` tasks with their
   `fields.key` — those keys ARE registry ids, so a
   journey the plan already names is never registered under a second id.
   Exit 4 (no plan) is fine: the registry alone is the truth.
3. If `sessions.json` already records this session with `testedAt`, say so and
   stop unless the user asked for a regeneration.

## Phase 1 — detect the framework per surface

- A session whose `session.meta.platform` is ios/android is an
  **Expo/React Native surface** → **Appium/WebdriverIO**.
- Web hosts → **Playwright**.
- Confirm against the repo: existing `playwright.config.*`, `wdio.conf.*`,
  `e2e/` layout, and `.vitrinka/project.json` when present. The repo's
  existing conventions WIN over defaults — new tests land beside the old ones,
  in their style. A session spanning both surfaces yields tests in both
  runners, one journey each.

## Phase 2 — map steps into journeys

Segment the digest's step walk into coherent journeys (a journey = one user
intent, typically 3–15 steps):

- Route clusters + the user's notes are the segmentation signal; a return to
  the home/entry screen usually ends a journey.
- Name journeys by intent (`orders-create`, `profile-edit`), not by session
  (`session-7-part-2` is forbidden — journeys outlive their source session).
- Steps stained by KNOWN open issues (digest `issues`) are still mapped — the
  test asserts the CORRECT behavior and is marked `expectedFail` until the fix
  lands (link the issue in the registry entry), never asserts the bug.

## Phase 3 — consolidation verdicts (before ANY code)

For each mapped journey, against the registry + a repo test scan:

| Verdict | When | Action |
|---|---|---|
| **skip** | An active registry journey already covers the same intent + routes | Add this session to its `sources`, nothing else |
| **extend** | Existing journey covers a prefix/subset — the recording goes further | Grow THAT test; never fork a near-copy |
| **update** | Existing journey's flow changed (routes/selectors moved) | Rewrite the existing test to the new reality |
| **new** | No registry or repo test covers the intent | Emit a new journey test |

User journeys legitimately differ even on shared functionality: two
journeys touching the same screens with different intent are BOTH kept — the
dedup target is the **reusable-block layer**, not the journey list. Extract
shared page interactions (login, navigation, list filters) into the repo's
PageObject/helper convention (create `e2e/blocks/` or the repo's equivalent if
none exists) and register them under `blocks`. A journey test file composes
blocks + its own intent-specific steps; it never re-implements a block inline.

Present the verdict table (journey → verdict → target file) in your session
before writing code — it is the run's spine.

## Phase 4 — emit through the e2e engine

Delegate the actual driving + emission to the **e2e skill** (the global
`e2e` skill when available — it drives the app live and emits runner-backed
tests; otherwise follow the repo's own e2e conventions by example). Per
journey give it: the step walk (routes, actions, quoted step notes), the
target framework + file, the blocks to reuse, and the verdict (extend = the
existing file, new = the target path).

- Selectors come from driving the LIVE app (the digest's click text/selectors
  are hints, not gospel — the recorder captured what WAS, the runner needs
  what's stable: testIDs > roles > text).
- Run each emitted/updated test against the dev stack per the repo's rules
  before calling it done. A test that never ran green does not enter the
  registry as `active` — mark it `draft` with the blocker noted.

## Phase 5 — record and stamp

1. Write `.vitrinka/journeys.json` — every touched journey: tests, blocks,
   routes, `sources` += this session, status (`active`/`draft`/`expectedFail`),
   `updatedAt`, and `task: <journeyId>` when a `journey` task of the same
   `key` exists in the QA plan (Phase 0).
1b. Round-trip the key into the plan: for every journey with a `task`,
   `update_task {id: <journeyId>, fields: {test: "<primary spec path>"}}`
   and `add_task_ref {id: <journeyId>, kind: "session", ref: "<session
   board slug>"}`; a journey the plan lacks but the recording proved is
   NOT created here — list it under "plan gaps" in the close-out so the
   tasks skill's "Journeys" recipe can add it under the qa task.
2. Write `.vitrinka/sessions.json` — this session: board, `testedAt`,
   `testBranch`, `journeys` touched (`testPr` once the PR exists — a commit
   can't embed its own hash; the branch is the durable pointer).
3. Commit manifests WITH the tests (one commit — the registry must never
   drift from the files it describes).
4. Stamp the server so /sessions shows progress:
   `PATCH /api/v1/sessions/{id}` body
   `{"pipeline":{"tested":"<ISO now>","journeys":[…],"testPr":"<url|commit>"}}`
   (always send the Bearer token from `$VITRINKA_TOKEN` / `vitrinka token`
   via stdin, never argv).
5. End with: the verdict table with outcomes, files written, blocks
   extracted/reused, test run results, and anything left `draft`.

## Token & API economy

| Instead of | Do |
|---|---|
| `/events` stream or `scrape_board` | `get_session` once |
| Reading step screenshots | the digest's routes/actions/notes; shots only if a step is genuinely ambiguous, via ONE batched subagent |
| One subagent per journey | emit sequentially in-session, or batch 3–5 journeys per subagent for large sessions (≤4 subagents) |
| Inventing test structure | the repo's existing e2e conventions + the e2e skill's emission rules |

## Red flags — STOP

- You are writing a test file without a verdict table entry for it.
- A new test re-implements login/navigation inline instead of using a block.
- A journey is named after the session instead of the user intent.
- A test asserts today's buggy behavior instead of `expectedFail`.
- The manifests and the test files are heading into different commits.
- You planned more than 4 subagents.
