# Surface: standalone — self-contained interactive documents

Author a **self-contained artifact** (report, analysis, review, dashboard, showcase) and deploy it to vitrinka. There is **no build step**: pushing the file IS the deployment — the share link is live in under a second, and every re-push updates the same URL.
pin: e2e/artifact-refresh.spec.ts#an ordinary reload after a push shows the new revision; unchanged assets stay cacheable

Capturing UI work in progress belongs to the **publish** skill; delegation to `vitrinka-publisher` per Shared core in `../SKILL.md`.

## Workflow

1. **Scaffold**: `vitrinka artifact init --slug <slug> --kind <report|analysis> --title "<Human title>"` → `.vitrinka/artifacts/<slug>/` with an editable `index.html` (import map: `react`, `htm`, `kit-3`, `zipstore-1`; the load-bearing theme contract) and a `doc.json` skeleton that renders through kit-3's `<Doc>` out of the box. From this session's screenshot set instead: `vitrinka artifact-from-set --slug <slug> [--select 1,3-5]`.
2. **Fill** — data-first by default: author only `doc.json`, never open `index.html`; the push validates every block server-side and the kit owns every visual decision. An architecture diagram is a first-class block: `{kind:"diagram", title, caption?, …}` carrying the exact board diagram-card semantics (lanes/groups/nodes/edges, no coordinates — vocabulary: `diagram.md`, this directory), ≤12 per doc; the server lays it out and scores it at push, and the diagram paints LIVE through the one React painter (board, solo view, press) — there are no stored SVG stamps; never author `geo` or `render` (a stale `render` copied from an older doc is dropped at push).
   pin: e2e/render-audit.spec.ts#the pushed document paints its diagram live, loads figures eagerly and keeps section edges aligned
   Iterate from your AUTHORED doc.json, never by re-pushing the stored stamped bytes: stamped geo/metrics would count against the 2 MiB authored cap and ride as authored content until overwritten. Compose components only when the document needs behavior or a block that doesn't exist: edit `index.html`, replacing or surrounding `<Doc>` with kit-3 components in htm.
   **Layout and nesting are blocks, not markup**: `{kind:"columns", ratio?, cols:[{blocks}]}` is the ONE horizontal grammar (2–3 columns, collapses when narrow — a score strip beside its verdict, a meter beside its chart; never prose); `{kind:"ref", card|page, mode?: link|preview|embed}` points at another document card — `page` names a sibling page slug inside the same push, the server resolves it and stamps `target` (never author `target`). A `timeline` takes `axis: spine|time` (spine default; `time` needs parseable `when` dates and falls back to spine).
3. **Look up, don't recall.** Every shape table, prop list, chart form and component palette lives in the deploy's own docs layer — the `docs` MCP tool, or `vitrinka docs <topic>` (`vitrinka docs` for the index). Topics: `docjson` (the block vocabulary), `charts` (the viz language), `scaffold`, `theme`, `shelf` (the vendored runtime), `design`, `gotchas`, plus one per kit component and one per element kind (`element:chart`, `element:table`, …). The docs are generated from the validator and kit the deploy actually serves, so they never drift — trust them over anything remembered. Validation is **strict canonical**: fields the contract doesn't name reject the push (no silent pruning).
   pin: e2e/artifact-theme.spec.ts#a doc.json that breaks the contract is rejected at push with the exact message
4. **Push**: `vitrinka push --root .vitrinka/artifacts/<slug> --title "<Human title>"`.
5. **Verify, then iterate**: read the push's diagnostics AND `render.png` beside the artifact — the proof the page renders, not just serves. A render error (`render.console`, blank `render.root`) is unfinished work even though the push succeeded: fix and re-push (same key → same URL). doc.json mistakes reject with exact machine-readable diagnostics; mechanical typos are autofixed at preflight (`fixed:` lines, `--no-fix` disables). Diagnostics carry `see` pointers into the docs layer — follow them. Diagram blocks report through the same envelope: composition findings arrive `blocks[i]`-prefixed with verified `fixes` (measured deltas) — apply at most one diagnosed fix per round, ≤2 rounds, report leftovers truthfully (the quality loop, `diagram.md`).
   pin: internal/docspec/autofix_test.go#TestAutofixEnumNearMisses

## Laws that stay in force while composing

- **Compose kit blocks first; never re-implement a kit block.** Bespoke markup only for what no block expresses.
- **The theme contract in `<head>` is load-bearing**: bespoke markup styles with the tokens (`--bg/--surface/--ink/--muted/--rule/--accent`; Tailwind arbitrary values read them: `text-[var(--muted)]`) — never hardcode a palette, never delete the block.
  pin: e2e/artifact-theme.spec.ts#semantic artifact themes natively in both directions and decodes entities
- **htm renders HTML entities literally** — write `→`, `·`, `—`, never `&rarr;` (preflight decodes them outside code/html blocks).
  pin: internal/docspec/autofix_test.go#TestAutofixDecodesEntitiesExceptCodeAndHTML
- **Tone is explicit meaning, never sign-inference.** A number only colors when you state its meaning (`tone: good|warn|bad|neutral`) — +79% frame time is *bad* despite the plus sign.
  pin: e2e/artifact-theme.spec.ts#presentation blocks: top-level rhythm, explicit tones, charts, meter, compare
- **A finding must carry its proof**: `status`, `cause`, `summary`, `evidence` — the exact log, file, query or check. A finding without evidence reads as an opinion.
- **A repo `DESIGN.md` is the style authority** (tokens + prose brief; discovered and sent with every artifact push — `design: <path>` in the narration; resolution is server-side: repo ▸ workspace DESIGN ▸ kit presets; explicit `meta.direction`/`meta.accentColor` always win). Pick `meta.direction` deliberately — `editorial · dossier · terminal · gallery` are four genuinely distinct identities.
  pin: e2e/artifact-design.spec.ts#stamped DESIGN tokens apply as defaults: direction, density, accent
  pin: e2e/artifact-design.spec.ts#explicit doc.json meta beats the DESIGN layer
- **Never drive Playwright/Chrome to "check it renders"** — the viewer is login-gated and the push's own render already saw the page. Where no screenshot came back, fall back to a token curl (Bearer header via stdin, never argv). **The link goes in your final summary, always.**
- The artifact appears on its project's home under the **Artifacts** tab (and on the project's artifacts board), labeled by title — pick a real `--title`. The project slug comes from the committed `.vitrinka/project.json`; `--project` only overrides.
  pin: e2e/artifact-theme.spec.ts#artifacts list under the project's Artifacts tab, apart from the journey versions
- **A semantic push also mints/updates a `doc` card** on the project's artifacts board (keyed by project/branch/slug, versioned — the ⌥ fan recovers old pushes) and the response carries its solo `element:` URL (`/a/<card>`) beside the set URL. Hand back what the push prints (field names: `../../publish/references/wire-fields.md`). Blocks with no canonical element yet skip the card with an advisory diagnostic — the set + raw view stay authoritative for those.
  pin: e2e/render-audit.spec.ts#a fully canonical document mints its doc card and the solo view paints every block, nested diagram included
- **Multi-page artifacts are a `pages/` directory, one push** (artifact-register decision #10): `pages/<slug>.json` beside `doc.json` — each a FULL doc.json (meta + blocks, same validator, same diagram stamping, slug = lowercase/digits/hyphens ≤64). The root and any page point at a sibling with `{kind:"ref", page:"<slug>", mode?: link|preview|embed}`; `vitrinka push` sends the whole directory as today (nothing new on the wire), preflights every page, and refuses a `page` with no file — the server rejects the same, naming the path (`pages/rizika.json:blocks[2].page`). One push mints the root AND one `doc` card per page on the artifacts board (one shelf run, keyed by set + slug so a re-push updates the same cards), rewrites page refs into card refs, stamps each ref's `target` and draws the `ref` wires — the board's `arrange {mode:"graph"}` lays the tree out and the solo view's outline rail walks it. The response adds `pages: [{slug, url, cardId}]` (`--json` too); the CLI prints one `page <slug>: <url>` line each. Cycles are fine (a back-edge). Hand back the root URL plus the page lines.
  pin: internal/web/push_pages_test.go#TestPushPages_MintsCardsRewritesRefsAndWires

Everything else — block shapes, meta fields, chart data forms, the runtime shelf, sandbox and offline gotchas — is `vitrinka docs`, not this file.
