# Brainstorm board — full flow and payload contracts

Read alongside the SKILL.md "Visual surface" section, which owns the
board-vs-terminal judgment and the just-in-time offer. This file owns the
mechanics.

**Reliable writes:** pass a stable `requestKey` on `compose_board` and `update_cards` for one logical operation. Retry identical accepted input with that same key after a lost response; the server returns the original compact receipt without duplicating cards or edits. Changed input needs a new key; reusing the old key returns 409. REST also accepts `Idempotency-Key` (both names must agree). Batch validation, saved parent/order, final layout and history commit together. Read the returned card IDs and refs for follow-up edits; let the server size and position the structured composition. A saved-template retry replays the first committed expansion even if the template has since changed.

**Board reading order — brainstorm boards are DOCUMENTS (book-flow 2026-08-28):** compose in narrative order and NEVER pass x/y. The `decision-map` template automatically puts the board in `flow: "document"` — top-level blocks stack top-to-bottom in compose order (every decision is its own chapter section, laying its members out inside — the entry first, its diagrams and takes beside it), and the mode STICKS: every later free batch on that board starts a new row below instead of continuing shelf rows. Scroll direction IS the reading order: ground-truth imports → the map heading → one chapter per decision (its per-option diagrams and takes INSIDE it) → working-notes section → log page. A batch composed out of order lands out of order — there is no re-shuffle step. (Non-brainstorm spatial boards keep the default aspect-packed shelf rows; opt any board in with the top-level `flow: "document"` param.)

**Say how the batch FLOWS — use the canvas (compose-layout D3/D4, 2026-08-27).** The compose vocabulary carries real layout intent; use it instead of accepting a tall column:

- "these three on one row" = an UNTITLED cluster `{kind:"cluster", payload:{layout:{mode:"row"}}, children:[…]}` — untitled clusters render NO chrome (no box, no label), pure grouping. `{mode:"grid", cols:N}` for N-across.
- Sections take `payload.description` — one quiet line under the kicker title that orients a newcomer; frames render as HEADED GROUPS (title + description, border only on hover/selection), so members' own card faces are the only boxes.
- The top-level `aspect` param (0/omit = 1.6, clamped [1, 3.2]) sets the shelf target per batch: wider (2.2–3) spreads a shallow narrative across the canvas, squarer (1–1.3) suits deep stacks.

**Before any mockup, load the design system.** Mockups must reflect the project's REAL design system: resolve and read the surface's `DESIGN.md` (per-surface in monorepos — e.g. `apps/client/DESIGN.md` vs `apps/web/DESIGN.md`; ask if ambiguous) and build every variant from its actual tokens. If none exists, offer to create one first (the `learn-design` skill).

**Mechanics** (vitrinka MCP tools first, raw API as fallback; artifact bundles are self-contained single-file HTML — no external hosts, same contract as the `artifact` skill):

1. **Create the board** (idempotent, 409 = reuse):
   `POST {base}/api/v1/boards` body `{"slug":"<project>-brainstorm-<topic>","title":"…","board_type":"brainstorm","project":"<project>","subgroup":"brainstorming"}` — the project field files it under that project's group in the sidebar; the subgroup folds it under the project's *brainstorming* sub-group (the server also infers `brainstorming` from the board_type when subgroup is omitted; projectless boards fall back to the *Brainstorming* type group). A board whose deliverable is design directions/mockups rather than a decision map takes `"subgroup":"design"` instead — `design` is never inferred, always pass it.
2. **Compose the decision map with the BUILT-IN `decision-map` template — one `compose_board` call** (brainstorm-board-v2 2026-07-17): `{"template": "decision-map", "params": {"title": "…", "context": "2-3 lines — what exists, what's missing", "decisions": [{"key": "D1", "title": "…", "stakes": "…", "options": [{"label": "…", "hint": "why / tradeoff", "recommended": true}], "multiSelect": false}, …]}}`. The server lays the whole map out deterministically as DECISION CHAPTERS (brainstorm-chapters D1 2026-09-04): a wide context strip, then ONE `section` PER DECISION titled with the decision heading — exactly `"<key> · <title>"`, e.g. `D1 · Board grammar` — described by its stakes, laying its members on a row: the one-line dotted-leader entry (key · title ······ state, the question anchored to it) first, the decision's evidence beside it. There is no outer map section. **The chapter title IS the landing contract**: `compose_board {section: "D1 · Board grammar"}` and `POST …/artifact {section: "D1 · Board grammar"}` drop cards into that decision's chapter, which grows to fit; a decision with no evidence stays a slim single-row chapter. Answering lives in the operator's docked question brief (the margin panel); the entry shows the frontier glow while open and the call once answered, and the camera frames the active chapter. Never hand-compose the v1 heading + idea-card + question column (it renders as an unscannable serpentine). Option `hint`s render VISIBLY under each label and `recommended` shows as ★ — put your recommendation's why in the hint, always. **Options keep their NATURAL order** (A, B, C…; chronological; small→large — whatever the fork's own logic is): never reorder to put the recommended option first — ★ already carries the recommendation, and a B-first list breaks the reading flow (user call, 2026-08-28). The terminal `AskUserQuestion` recommendation-first rule is terminal-only. A decision the user should answer in prose takes `"kind": "text"` instead of options (renders as an inline write-in). Max 12 decisions — a bigger map means the brainstorm needs splitting.
   **Existing system? Import the ground truth** (adoption 2026-07-18): when the topic concerns an existing system with an importable truth source — `docker-compose.yml` (`compose`), an OpenAPI spec (`openapi`), SQL DDL (`sqlddl`), a live Postgres (`pgschema`) — place a refreshable "what exists today" diagram beside the context strip: `REV=$(git rev-parse --short HEAD); vitrinka import <file> --board <slug> --rev "$REV"` (raw: `POST {base}/api/v1/boards/{slug}/import {kind, source, ref, rev, title}`). Options get argued against the real system, not prose recollection — and ↻ keeps the diagram honest if the brainstorm outlives a code change. Skip when the topic is greenfield.
3. **Brainstorm around the fork with the cheap vocabulary before reaching for mockups**: `cluster` frames per direction (`children: [refs]`) holding `idea`/`pro`/`con`/`risk` text cards; a `chart` card for structure — `matrix` (effort × impact), `flow` (step order), `bars`/`timeline`, real charts (`line/area/scatter/pie/donut/heatmap` — recharts-shaped `{series|items}` data, axes + tooltips come free) when the fork is data-shaped; a `table` card (typed columns — options × criteria) when the fork is a comparison grid; a `diagram` card when the fork is ARCHITECTURE-shaped (lanes/groups/nodes/styled edges — a whole system page in one card, server-laid-out). **For an architecture fork, typed v2 diagrams per option are THE standard, not optional prose** (adoption 2026-07-18): one small diagram card per competing architecture (typed nodes `service`/`entity`/`endpoint`, edge styles `default|public|mesh|internal|outbound` — `accent` is a node/group TONE, never an edge style; payload vocabulary in the artifact skill's `references/diagram.md` and the cheat sheet below), and the decision's options trace to them via **`cardRef` in the SAME compose call** — pass the diagram cards (each with a `ref`) alongside `template`/`params`, and each option carries `{"cardRef":"<that ref>"}` (the server resolves it to the created card's id; `cardId` still works for pre-existing cards). **Every card an option `cardRef`s lands INSIDE that decision's chapter automatically** (entry first, diagrams beside it in option order; a ref cited twice joins once, a ref cited by two decisions joins the first) — never wrap them in a section of your own or land them with `{section}`. A `cardId` option (a pre-existing card) is left where it is. One batch, same trace-wire + fly-on-pick contract as visual takes (step 4.3). Competing architectures must be visually comparable at a glance. A chart is ~100-300 tokens; an artifact is a whole HTML document — spend that only on step 4. For journey-shaped work, `section` frames (journey-named, always visible, pill-navigable) partition the board; scope later reads/writes with `scrape_board {section}`, `compose_board {section}` and `arrange {scope:"section:Name", gap, cols}`.
4. **Visual takes live INSIDE the decision's chapter** (brainstorm-chapters D1 2026-09-04 — replaces the 2026-07-12 "Take A — …" sections) — the predictable-layout contract, two calls total:
   1. Per take, `POST {base}/api/v1/boards/{slug}/artifact` with `{"body":"…","runtime":"tw4","tokens":{…},"title":"A — <name>","section":"<key> · <title>","device":"phone"|"tablet"|"web"}` (or `"html"` for a full document, ≤8 MiB) — `section` is the decision's CHAPTER TITLE exactly as the map composed it (`D3 · Panel anatomy`), never a "Take A — …" section of your own. The mockup lands INSIDE the chapter beside the entry (the chapter grows to fit) and the server measures its natural size — mocks always render whole, scaled to the card. A short tradeoffs text card per take, when wanted, goes in the same way: `compose_board {section: "<key> · <title>", cards: [...]}`. **Never send x/y or w/h; `device` is MANDATORY intent** (default is 16:10 web — phone mockups without `device:"phone"` render wrong). **Paint your own page**: the artifact iframe face is WHITE and blob URLs are immutable-cached. A dark `body`/`runtime:"tw4"` mockup must START with `<style>html,body{margin:0;background:<bg>}</style>` (a `min-h-screen` div does NOT reach the iframe edges; default body margin shows as a white ring) — a full `"html"` document instead styles its own `html`/`body` in its `<head>` (it must stay a real document; a fragment starting with `<style>` is rejected). Either way, tw4 markup uses raw `class=`, never JSX `className=`. Outside the grouped pattern, `"anchor": <cardId>` + `"side":"right"|"below"` docks a one-off mockup beside any card; coordinate-free posts land in free space, never at (0,0).
   2. Link the takes to the decision: `update_question {id, options: [{"label":"A — <name>","hint":"<why>","recommended":…,"cardId":<that take's artifact id from step 1>}, …]}` on the chapter's question (its id is in `get_questions`); a decision that only exists because of the takes composes as `{template:"decision-map", params:{title:<the map title>, extend:true, decisions:[…]}}` with `cardId` on each option instead. The board draws a quiet trace wire from the question to each option's mockup, hovering an option glows its trace, and picking zooms the camera to that take — never ship an option without its `cardId`.
5. **Refine in place, don't re-compose**: `update_cards` rewords your own cards (AI layer only) and removes what you own — AI-layer cards, section frames, cards you created — up to 25 per call / 30 % of the board. The user's content is gated, never untouchable: removing it answers `409 needs_confirm` with a `preview`; read it, repeat the same ids with `confirm:<token>` + a `reason` (≥ 20 chars). Removals are soft; the reason shows in HISTORY and the Trash tab, where the operator restores. Everything you place sits under the board's `✦ eve` toggle, so express freely.
6. **Hand over the URL**: give the user the `url` field the create-board response returned (step 1) — it is server-authoritative and carries the `/w/<workspace>` segment; never compose `{base}/boards/{slug}` yourself (it omits the workspace). Continue any terminal questions in parallel.
7. **Collect answers**: answers are STAGED on the board — the user picks options, then presses the board's "Send to Claude" (↑) to release them, so answers arrive as a BATCH of `choice` items on the work wire, not one per click (multi-select answers carry `options: [labels]`). A choice item may carry a **`note`** — the operator's clarifying words attached to the pick ("Owner hub — but keep the export button"): treat it as part of the answer, never ignore it. Answer/note text may contain **⌖E tokens** (the operator ⌥-pointed at board elements while writing); the item's **`refs`** array resolves each token — `{token, cardId, elemNo, region?, node?, crop}` with `crop` a ready image URL of exactly the pointed-at region — fetch the crop when the pointed pixels matter to the answer. A `kind: "text"` item's `option` IS the typed prose answer. Drain via the vitrinka MCP `wait_for_work` (`choices[]` array), or arm the listen skill's Monitor for zero-token idle (use its exact `exec vitrinka watch` command — a non-`exec` watch outlives the session and holds the board's lease forever); the MCP `get_questions {board}` reads the board's full question record without holding the wire (staged answers are visible but NOT yet sent — don't act on them). Choices ride the wire exactly ONCE — if a send happened while no session was listening (or the session died mid-brainstorm), the answers are NOT lost: `get_questions` is the durable record (answer, note, refs, answeredBy, staged/sent per question) — reconstruct the batch from it and write the log as usual. Record each answer — including notes — in the decision log like any other call. **The log page is LIVE**: after draining each batch, update the spec (answered rows flip to `[!status green](Decided)` with the call), commit, and `POST /cards/{id}/refresh` the log page — the user watches decisions settle on the board as they answer, not only at the end.
7b. **↻ REGENERATE — the operator's rework signal** (board-as-questionnaire D7 2026-08-26; replaces the retired 2026-08-22 auto-streaming live mode). Answers ALWAYS wait for the operator: picks stage, ↑ Send releases the batch, and **↻ Regenerate** releases it with `regenerate: true` stamped on every choice item — the explicit "my answers/notes changed the direction, rethink the open map" ask. Never retract, rewrite, or re-compose open questions off picks that have not been released, and never treat a drained plain batch as a rework request:
   1. **Plain ↑ batch**: record the answers in the log, and compose NEW dependent-round questions if settled answers opened them (`extend: true` — new chapters append below the last one). Existing open questions stay untouched.
   2. **↻ regenerate batch** (`regenerate: true` on its items): read it as this instruction from the operator — *"My answers and notes in this batch changed the direction enough that the remaining open questions and their options no longer fit. Discard them and compose a fresh frontier that follows the direction these answers set — reread my notes and Other write-ins first; they carry the redirect."* The client confirmed the discard before sending, so regenerate without re-asking. First `board_working {board, status: "recomposing — rethinking N questions…", expected: N}` so the board never looks stuck, then regenerate as retract + replace, one living map: `retract_questions {ids}` withdraws your stale OPEN questions (never the operator's answered/staged ones — those 409 per item) and `update_cards {remove: [ids]}` removes their chapter sections in the same breath — list the section id AND the entry / evidence card ids inside it (trashing a frame never trashes its members; `scrape_board {section: "<key> · <title>"}` lists them); `update_question` rewords a fork that survived in changed shape. Then compose the next frontier: `{template: "decision-map", params: {title: <the SAME map title>, extend: true, decisions: […]}}` — extend skips the heading and appends one chapter per decision below the existing ones, so rounds grow ONE map instead of stacking dead sections. Do NOT pass `section` — chapters have no wrapper frame. Retracted rows stay visible to you in `get_questions` (`retracted: true`) as the durable record — never re-ask them verbatim.
   3. **Pivot flags still matter**: mark map-reshaping decisions/options `"pivot": true` — the board renders the emphasis so the operator knows which answer redirects the map (and which pick deserves a ↻) — but the flag no longer streams or flushes anything.
   4. **Log per batch**: refresh the log page after each drained batch (step 7) — that is the natural rhythm now.
7c. **✦ ASK-AI info requests** (questions-ux wave2 W7) — `asks[]` items (`{type:"ask"}`) on the same wire, arriving IMMEDIATELY (an ask is an explicit action, never staged): the operator, mid-selection, wants more information about ONE question — context, tradeoffs, what the codebase actually does — before picking. Service asks FIRST (the operator is watching a ● working popover live), before any batch work. Answer by STREAMING via `answer_ask {id, text, partial:true}` in 2-4 sentence-sized chunks, final chunk without `partial` (settles ✓ done; `failed:true` + a reason settles ✗ failed). Ground the answer in the real system — read the code if the ask is about behavior — and keep it popover-sized: the item carries the question's prompt, stakes and option labels, so answer about THOSE, not in general. An ask never changes the map: no retracts, no recompose, no code edits.
8. **Settle: finalize the log, graduate** (adoption 2026-07-18) — when all map questions are answered:
   1. **Log page card, mdfile-backed, born WITH the board**: the initial build already composed the log page (all rows Open) as `{"kind":"page","payload":{"md":"<log md>","source":{"kind":"mdfile","ref":"docs/specs/<file>.md","rev":"<git short SHA>"}}}` — the spec file and the board page are ONE artifact, kept in step with step 7's live refreshes. At settle, commit the final spec and push the last `POST {base}/api/v1/cards/{id}/refresh {source:<md>, rev:<new SHA>}`; if a human block-edited the page meanwhile, run the write-back loop from the artifact skill's `references/pages.md` first.
   2. **The log is a live index, not a prose mirror**: format the spec's decision table as `:::table` with a status column of `[!status green](Decided)` lozenges (`[!status yellow](Open)` for deferred), a `[!date](YYYY-MM-DD)` chip in the header line, and per-row `#E<elemNo>` links to each decision's tile (elemNos come from the compose response or `scrape_board`) — clicking a row flies+pulses to the tile that settled it. The rich syntax lives in the committed file too; it degrades to literal text outside the board, never an error.
   3. **Graduate to the docs board, automatically** (no ask): find the project's docs board (`list_boards {project}`), create it fully-specified if missing (`create_board {slug:"<project>-docs", board_type:"docs", project, subgroup:"docs"}` — 409 = reuse), then push the log page (same mdfile-backed contract, into the **Pages** section) and re-compose the WINNING architecture diagram (into **Architecture**) — re-compose, don't move: the brainstorm board keeps its full option history. `#E<elemNo>` links are BOARD-LOCAL — strip them (or retarget to the graduated diagram's elemNo) in the docs copy, or they fly to the wrong cards. Hand back both board URLs.

**Payload cheat sheet** — the shapes below are the CANONICAL element vocabulary (migrate-and-drop 2026-09-01; the retired `viz` kind and its payload shapes 400 with the canonical kind). Full per-kind contracts: the `docs` MCP tool (`docs {topic:"<kind>"}`) — generated from the validator, never stale; kind index + doctrine: the publish skill's `references/card-kinds.md`:

```
text     {"kind":"text","payload":{"md":"…","role":"idea|pro|con|risk"}}
         idea/pro/con/risk are ROLES on text cards — never card kinds
heading  {"kind":"text","payload":{"md":"# …","role":"heading","level":1|2|3}} — the editorial ladder (30/22/17px):
         level 1 = the board's H1 (decision-map mints its own), 2 = chapter intro, 3 = sub-heading; deeper #s step down a tier
chart    {"kind":"chart","payload":{"viz":"<viz>","title":"…"?,"caption":"…"?,"data":{…}}}   viz + data are REQUIRED; fill the ONE slot the viz reads:
         viz line|area|bars|scatter → data.series [{"label":"web","points":[120,180,240]}] (+ "x":["W1","W2","W3"] categories;
           scatter points are [x,y] pairs ONLY; bars also accepts data.items labeled rows) · "stack":true groups→stacks
         viz pie|donut|bars → data.items [{"label":"…","value":<number>}]        viz stat → items [{"label","value","delta"?,"unit"?,"tone":"good|warn|bad|neutral"?}]
         viz timeline → items [{"label","when":"2026-09-05"}] · viz matrix → items [{"label","x":0..1,"y":0..1}] · viz flow → items [{"label"}]
         viz heatmap → data {"x":[<col labels>],"y":[<row labels>],"values":[[n,…],…]} — one row of numbers per y label
         (a "table" is a KIND, never a viz — the retired viz:"table" 400s)
table    {"kind":"table","payload":{"title":"…"?,"caption":"…"?,"cols":[{"key":"opt","label":"Option","type":"text|number|date|select|check|link"}],
                                    "rows":[{"opt":"Hub","score":3}]}}
         rows are objects KEYED BY COL KEY (no "id" field, never positional arrays); every row key must be a declared col key
         (unknown key = 400); type defaults to text; select cols carry "options":[…]
diagram  {"kind":"diagram","payload":{"title":"…","dir":"LR"?,"nodes":[{"id":"api","title":"API","type":"box|service|entity|endpoint|note"}],
                                      "edges":[{"from":"api","to":"db","style":"default|public|mesh|internal|outbound","label":"…"?}]}}
         nodes carry title, NEVER label (id auto-assigns n1, n2… when omitted; edges reference ids, or node.port)
         edge style has NO accent — accent is a node/group "tone" (default|public|mesh|internal|outbound|accent)
         lanes [{"label":"…","nodes":[…]}] (label, not title) · groups [{"title":"…","tone":"…"?,"nodes":[…]}] (title, no id needed)
         entity columns [{"name":"…","type":"…","pk":true,"fk":"table.col"}] — fk is a STRING ref, not a bool
         endpoint titled "POST /path" derives its method chip + path; omit w/h (natural size, no upscale)
frames   {"kind":"cluster|section","children":["ref",…],"payload":{"title":"…","description":"…"?,"layout":{"mode":"row|grid|column","cols":N,"gap":N}}}
         children order is reading order, independent of cards array order; payload.layout retains the frame's arrangement
         untitled cluster = chrome-free row/col group (no box, no label); section description = one quiet line under the kicker
aspect   top-level compose param {aspect: 2.4} — shelf target w/h (omit = 1.6, clamp [1, 3.2]); spread wide narratives, don't stack them
flow     top-level compose param {"flow":"document"} — chaptered top-to-bottom reading order, sticky on the board;
         the decision-map template sets it automatically (book-flow 2026-08-28)
page     {"kind":"page","payload":{"md":"…","source":{"kind":"mdfile","ref":"docs/specs/….md","rev":"<short sha>"}}}
option   {"label":"…","hint":"…","recommended":true, "pivot":true?, "cardRef":"<ref in THIS batch>" | "cardId":<existing id>}
         options stay in NATURAL order (A/B/C…) — ★ marks the recommendation; never sort recommended-first on a board
pivot    decisions take "pivot":true (question-level) or per-option — marks the map-reshaping fork (render emphasis only; nothing streams)
extend   decision-map params {"extend":true} appends one chapter per decision below the map, no heading (next rounds)
chapter  every decision composes as a section titled "<key> · <title>" (D1 · Board grammar) with description = stakes;
         {section:"<that title>"} on compose_board / POST …/artifact lands takes INSIDE it; option cardRef cards join it automatically
stakes   first-class on questions (v82): decision-map flows each decision's stakes onto its question automatically;
         ask_board / compose questions / update_question take "stakes" directly — the answering panel renders it
         under the prompt and the choice work item echoes it, so ALWAYS pass it for decision-shaped questions
verdict  choice items from brainstorm boards may carry {ranking:[best-first], discarded:[]} — the stage's organizing
         gesture (v83). Read it as the operator's whole preference: log runners-up and dead options, not just the pick
```

**Fallback ladder** — never block the brainstorm on the board, and always SAY which rung you're on: `compose_board` → (tool missing / 404 = older deploy) `ask_board` + artifact cards → (server unreachable) terminal-only `AskUserQuestion`.
